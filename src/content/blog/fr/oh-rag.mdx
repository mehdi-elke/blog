Je m'en souviens comme si c'était hier, une issue GitHub qui me remontait que les réponses de mon agent ne fonctionnaient pas : des ressources qui n'existaient plus étaient utilisées pour générer les réponses, des anciennes versions prises en compte ou même des nouvelles classes qui n'étaient pas trouvées. Quelques captures d'écran me mettent le tout sous le nez... Oh RAG, oh désespoir, oh vieillesse ennemie...

Le RAG vieillit mal et corrompt la fenêtre de contexte d'OllamAssist en moins d'un acte. Pas top comme comportement, mais on dirait qu'il y a autre chose... mais quoi ?


## Le RAG Vectoriel : Une bibliothèque de scripts

Le RAG permet de récupérer des infos qui ne sont pas directement stockées dans le modèle. Ici, je présente le RAG vectoriel, c'est-à-dire l'utilisation d'une base de données vectorielle pour stocker les informations et récupérer les données "les plus proches sémantiquement" pour aider le LLM à répondre à la demande.

`} />

Mais avant d'aller un peu plus loin, il vaudrait mieux que je pose quelques bases au niveau des connaissances des LLMs. 
Pour faire court, un LLM permet de prévoir les prochaines chaînes de caractères en fonction de probabilités. Toutes ces connaissances sont acquises en entraînant le modèle à partir de données, et actuellement les LLM les plus couramment utilisés sont entraînés à partir de ce que les internets contiennent. C'est-à-dire beaucoup, beaucoup, mais vraiment beaucoup de données. 

Grâce à cela, un LLM peut répondre à des questions génériques du type "quelle est la capitale de la France ?", "explique-moi comment fonctionne Redis"... sans aucune difficulté. Par contre, comment faire pour que le LLM puisse répondre à des questions liées aux données de l'entreprise ou d'autres sources de données privées, qui ne sont pas publiques et n'ont pas pu (je l'espère) être accessibles au cours de l'entraînement du modèle ?

Plusieurs approches possibles : on peut soit ré-entraîner un modèle avec ces nouvelles données (ce que l'on appelle le fine-tuning) et l'utiliser, mais ce type d'approche est excessivement lourd et peu performant finalement.
Une autre approche serait de fournir les données au LLM liées à la question et en lui demandant d'utiliser ces documents pour répondre à la question.

La deuxième approche est la plus couramment utilisée car moins chère et plus rapide à mettre en place. Traditionnellement, on indexe toutes les informations pertinentes dans une base de données vectorielle (ChromaDB, DuckDB...) et on recherche les documents les plus proches sémantiquement en récupérant ceux ayant la "distance" la plus petite possible.

Vous pouvez le deviner facilement, cette approche bien que moins coûteuse a aussi un coût : l'indexation des documents, la "transformation" en vecteur pour l'insérer dans la base de données et la récupération de documents en fonction de la question.

Le RAG (*Retrieval-Augmented Generation*) correspond à cette deuxième approche et c'est celle qui est utilisée dans OllamAssist pour l'aider à répondre aux questions.

## Le Drame du Context Shift : Un script qui prend la poussière

Mais le RAG a un gros problème : le *context shift*. Les données indexées en base de données peuvent "doucement" se désynchroniser des données d'origine, ce qui aboutit à une corruption de données qui impacte la qualité des réponses.

<Mermaid code={`
sequenceDiagram
    participant Code as Code (Vérité Terrain)
    participant DB as Vector DB (Cache)
    participant LLM as LLM
    
    Code->>DB: Indexation Initiale (v1)
    Note over Code: Le développeur modifie le code (v2)
    Note over DB: L'index reste en v1 (Stale Cache)
    User->>LLM: Pose une question sur v2
    DB-->>LLM: Envoie le contexte v1
    LLM-->>User: Réponse périmée (Désastre !)
`} />
<p class="text-center text-xs text-muted-dynamic -mt-10 mb-10 font-mono uppercase tracking-widest">Fig 2. La tragédie de la désynchronisation (Context Shift)</p>

En gros, c'est le drame classique de la désynchronisation, ce qu'on appelle souvent un problème de **Stale Cache** (un cache périmé). Dans la vraie vie d’un projet, votre code et votre doc bougent constamment en coulisses : on coupe des répliques (le code mort), on réécrit une scène (une méthode) ou on ajoute de nouveaux personnages (des classes). Le problème, c'est que votre base vectorielle n’a pas reçu le nouveau script. Elle reste complètement figée dans le passé, prête à réciter le texte du jour de sa toute première indexation.

C’est là que la tragédie se joue. Quand l’utilisateur pose une question, votre moteur de recherche va jouer les souffleurs auprès du LLM en lui injectant de vieilles répliques périmées sous prétexte qu'elles sont "sémantiquement proches". Le LLM, qui fait bêtement confiance aux lignes qu'on lui donne, entre en scène et déclame une réponse basée sur un passé qui n'existe plus. Rideau. Ce décalage fatal entre la pièce qui tourne réellement dans votre code et le vieux script coincé dans votre base de données, c'est ça, le _context shift_. Et c'est exactement comme ça qu'OllamAssist se retrouve à saboter sa propre représentation en moins d'un acte.

## Le RAG Vectorless : Pas de script, pas de problème

Une solution possible dans le cadre d'OllamAssist est le RAG *vectorless* : on recherche directement dans les documents sans indexer les données. Sans projection, pas de *shift*.

    IDE --> Context[Code Vivant]

    User --> LLM
    LLM --> Result[Réponse Toujours Fraîche]

`} />

Évidemment, ma première réaction a été de vouloir patcher le script en temps réel. J'ai branché un _listener_ sur le workspace pour surveiller le moindre changement : un fichier modifié, supprimé ou ajouté, et hop, on réindexe à la volée. Sauf qu'en pratique, le souffleur passait son temps à réécrire la pièce à la moindre frappe de clavier, provoquant une indexation incessante. Pour calmer le jeu et éviter la surchauffe, j’ai dû caler un _debouncer_. Ça fonctionnait à peu près... jusqu'au moment fatidique du switch de branche Git. Faire un `git checkout`, c'est l'équivalent de réécrire trois actes d'un coup en une fraction de seconde : le _listener_ s'affole, l'index s'emmêle complètement les pinceaux, et on se reprend le _context shift_ en pleine figure.

Pour éviter que la pièce ne tourne définitivement au fiasco, il a fallu changer radicalement de stratégie. Exit la base vectorielle et sa synchronisation impossible en coulisses. La vraie solution pour OllamAssist a été de se brancher directement sur le scénario en direct : l’API d’IntelliJ.

Au lieu d'essayer de courir après les fichiers, l'agent interroge l'IDE en temps réel. Dès qu'une question tombe, on scanne par mots-clés les classes et les méthodes directement dans le code vivant. On applique un petit réarrangement maison par-dessus pour ordonner et remonter les structures les plus pertinentes, et on injecte un contexte 100 % frais au LLM. Avec ces modifications, on pourra bientôt se passer de toute la phase d'indexation de données et alléger OllamAssist d'une partie gourmande en ressources.

Bien sûr, d'autres solutions sont possibles : construire un graph RAG, garder la synchronisation, envoyer les fichiers sur un serveur distant pour "décharger" ce coût sur une autre machine. Mais ce n'est pas ce que j'ai en tête pour OllamAssist. Je cherche à construire une solution fonctionnant en local, ce qui nécessite pas mal d'ajustements. 

C'est pour cette raison que je m'appuie sur une approche [LLM-as-a-Judge](/fr/blog/ragot-et-hallucination) : cela me permet de mesurer précisément mes avancées et d'en comprendre les impacts en temps réel. Le rideau n'est pas encore tombé sur OllamAssist, et les prochains actes s'annoncent riches en rebondissements.
